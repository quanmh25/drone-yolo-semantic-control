# Drone YOLO Semantic Control

A ROS 2 Jazzy and Gazebo Harmonic simulation combining RGB-D sensing, YOLO object detection, and distance-based drone control.

The drone takes off, moves forward, and stops based on the detected object class: a configured clearance of **2.0 m before a person** or **1.1 m before a car**, plus a stop margin and image-age compensation. Depth sensing also provides an emergency obstacle stop.

## How it works

`Gazebo RGB-D camera → YOLO + depth estimation → semantic controller → velocity commands`

- **drone_scene:** outdoor world, drone, front RGB-D camera, and ROS–Gazebo bridges.
- **drone_control:** synchronized RGB/depth perception, automatic takeoff, forward motion, and latched stopping.
- **Scene:** a road, crosswalk, sidewalks, parking area, three people, three cars, and five trees.

## Requirements

Ubuntu 24.04, ROS 2 Jazzy, Gazebo Harmonic, system Python 3.12, and a graphical environment. Install [ROS 2 Jazzy](https://docs.ros.org/en/jazzy/Installation/Ubuntu-Install-Debs.html) first. Internet access is needed for dependencies and the initial model download.

Run the following commands in Bash from the repository root.

## Setup

```bash
sudo apt update
sudo apt install ros-jazzy-ros-gz ros-jazzy-xacro \
  ros-jazzy-robot-state-publisher ros-jazzy-cv-bridge \
  ros-jazzy-message-filters ros-jazzy-rqt-image-view \
  python3-colcon-common-extensions python3-rosdep python3-venv python3-pytest
source /opt/ros/jazzy/setup.bash

# Run only if rosdep has not been initialized:
sudo rosdep init
rosdep update
rosdep install --from-paths ros_ws/src --ignore-src -r -y --rosdistro jazzy

# Create .venv, install CPU PyTorch and YOLO, and download models/yolov8n.pt.
bash ros_ws/src/drone_control/scripts/setup_yolo.sh

# Build using the system Python; leave the virtual environment inactive.
cd ros_ws
colcon build --symlink-install --packages-select drone_scene drone_control
cd ..
```

The setup script uses system site packages and pins NumPy/OpenCV for ROS `cv_bridge` compatibility. Scene assets are included in the repository.

## Run

```bash
# Person demo: take off, move forward, and stop.
bash ros_ws/src/drone_control/scripts/run_demo.sh

# Car demo: close the previous demo with Ctrl+C before starting this one.
bash ros_ws/src/drone_control/scripts/run_demo.sh x:=-4.0 y:=-6.0
```

The default spawn position is **`(-5, 1.5, 0.15)` m**, facing the person at `(0, 1.5)` m. The car demo spawns at **`(-4.0, -6.0, 0.15)` m**, facing the first parked car, `car_park_1`, at `(1.5, -6)` m. The second parked car, `car_park_2`, is farther along the same route at `(7.5, -6)` m. Parked cars use a 45° heading. The earlier validation used a spawn position of `(4.0, -6.0, 0.15)` m and targeted the second car; the new, longer approach needs a separate validation run.

The script sources ROS and the workspace, exposes the YOLO environment, and launches simulation, perception, and control. Stop with `Ctrl+C`; run one demo at a time.

To launch manually or use custom weights with class names `person` and `car`:

```bash
source /opt/ros/jazzy/setup.bash
source ros_ws/install/setup.bash
export PYTHONPATH="$PWD/.venv/lib/python3.12/site-packages:${PYTHONPATH:-}"
export YOLO_CONFIG_DIR="$PWD/.venv/yolo-config"
ros2 launch drone_control run.launch.py weights:="$PWD/models/yolov8n.pt"
```

For the scene alone, with the same default spawn position, source ROS and the workspace, then run:

```bash
ros2 launch drone_scene sim.launch.py
```

### Launch arguments

The demo script forwards additional arguments to `drone_control/run.launch.py`.

| Argument | Default | Purpose |
| --- | --- | --- |
| `weights` | Set by `run_demo.sh` | Local YOLO `.pt` file; required when launching manually |
| `start_sim` | `true` | Set to `false` to connect control and perception to an already running scene |
| `world` | `semantic_outdoor.sdf` | World filename within the installed `drone_scene/worlds` directory |
| `x`, `y`, `z` | `-5.0`, `1.5`, `0.15` | Drone spawn coordinates in meters |
| `gz_extra_args` | Empty | Additional Gazebo command-line arguments |

For example, after launching the scene separately, start perception and control with:

```bash
bash ros_ws/src/drone_control/scripts/run_demo.sh start_sim:=false
```

Use the same scene and topic configuration when running separately. Spawn and world arguments take effect only when `start_sim:=true`.

Earlier runs of the textured scene with the default YOLO weights reached `STOP_person` and `STOP_car`, using the spawn positions and parameters recorded in the validation report. See [validation results and annotated images](docs/validation/README.md). Recognition can still vary between frames and machines.

## Observe and configure

In another terminal, source ROS and the workspace, then run:

```bash
ros2 run rqt_image_view rqt_image_view   # Select /semantic/annotated.
ros2 topic echo /semantic/status       # Run in a separate terminal.
```

Detections are published as JSON on `/semantic/detections`. `STOP_person` and `STOP_car` indicate class-based stopping; `STOP_OBSTACLE` indicates a depth-only stop. Stops remain latched until reset or restart:

```bash
ros2 service call /semantic/reset std_srvs/srv/Trigger '{}'
```

Edit [`semantic.yaml`](ros_ws/src/drone_control/config/semantic.yaml) to tune behavior:

| Parameter | Default |
| --- | --- |
| Takeoff height above spawn | 1.1 m |
| Forward speed | 0.25 m/s |
| Person / car stop distance | 2.0 / 1.1 m |
| Additional stop margin | 0.10 m |
| Maximum horizontal displacement | 20 m |
| YOLO confidence / inference rate | 0.35 / 5 Hz |
| Inference device | CPU |

Distances are approximate forward clearances; margins and image latency compensation can cause earlier stops. Scene layout is defined in [`semantic_outdoor.sdf`](ros_ws/src/drone_scene/worlds/semantic_outdoor.sdf).

### Stopping distances

With the current YAML configuration, the stopping conditions in [`policy.py`](ros_ws/src/drone_control/drone_control/policy.py) are:

| Stop state | Condition on estimated clearance |
| --- | --- |
| `STOP_person` | At or below `2.0 + 0.10 + cruise_speed × image_age + 0.03` m |
| `STOP_car` | At or below `1.1 + 0.10 + cruise_speed × image_age + 0.03` m |
| `STOP_OBSTACLE` | At or below `0.65 + cruise_speed × image_age` m, using the depth-only obstacle estimate |

The class-based stops include the configured **0.10 m margin** and the policy's **0.03 m stopping tolerance**. At a cruise speed of **0.25 m/s** with an image age of **0.2 s**, the trigger thresholds are approximately **2.28 m for a person**, **1.38 m for a car**, and **0.70 m for a depth-only obstacle**. These are trigger thresholds, not guaranteed final physical distances. The obstacle rule uses a fixed 0.65 m base threshold in `policy.py` and does not add `stop_margin`.

Clearances are estimated from depth pixels with camera-angle and offset corrections; they are not center-to-center distances between the drone and objects. A `STOP_OBSTACLE` result demonstrates depth-based stopping, not successful person/car recognition. Setting a class distance too close can cause the depth-only stop to trigger first, especially if YOLO loses the target at close range.

The car setting is currently **1.1 m in YAML**; the earlier validation run used **1.0 m**, as recorded in the validation report. YAML values supplied by the launch file override Python defaults in `controller.py`.

The controller reads its parameters at startup. Restart the demo after editing configuration; rebuild the affected package if the installed copy does not reflect your changes.

### ROS interfaces

| Topic or service | ROS type | Purpose |
| --- | --- | --- |
| `/front_rgbd/image` | `sensor_msgs/msg/Image` | RGB input to perception |
| `/front_rgbd/depth_image` | `sensor_msgs/msg/Image` | Aligned depth input to perception |
| `/front_rgbd/camera_info` | `sensor_msgs/msg/CameraInfo` | Camera calibration |
| `/front_rgbd/points` | `sensor_msgs/msg/PointCloud2` | Bridged point cloud; not used by the control policy |
| `/odom` | `nav_msgs/msg/Odometry` | Drone pose feedback |
| `/cmd_vel` | `geometry_msgs/msg/Twist` | Controller velocity output to Gazebo |
| `/clock` | `rosgraph_msgs/msg/Clock` | Simulation time |
| `/tf` | `tf2_msgs/msg/TFMessage` | Bridged odometry transforms |
| `/semantic/annotated` | `sensor_msgs/msg/Image` | Detection boxes and estimated clearances |
| `/semantic/detections` | `std_msgs/msg/String` | JSON containing `stamp`, `objects`, and `obstacle_m` |
| `/semantic/status` | `std_msgs/msg/String` | JSON containing `state`, commanded velocities, timestamp, and perception data |
| `/semantic/reset` | `std_srvs/srv/Trigger` | Service that clears the stop latch |

Each detected object includes `class`, `confidence`, `bbox` (pixel coordinates), `distance_m`, and `in_path`. Missing depth is represented by JSON `null`. Only `person` and `car` detections are published; a bounding box overlapping the central 38–62% of the image width counts as in the flight path. Depth-only obstacle checks use a separate central image region.

### Controller states

The normal progression is `WAIT_ODOMETRY → TAKEOFF → CRUISE → APPROACH_person/car → STOP_person/car`, provided perception is available and the target is detected. The approach state is optional: an object already within the stopping threshold can trigger an immediate stop.

| State | Meaning |
| --- | --- |
| `WAIT_ODOMETRY` | Odometry is missing or stale; all commanded velocities are zero |
| `TAKEOFF` | Climbing toward the configured height above the initial position |
| `WAIT_PERCEPTION` | Perception is missing, malformed, stale, or timestamped in the future |
| `WAIT_DEPTH` / `WAIT_OBJECT_DEPTH` | Required obstacle or in-path object depth is unavailable |
| `HOLD_ALTITUDE` | Forward motion is paused while altitude is corrected |
| `CRUISE` | Moving forward at the configured speed |
| `APPROACH_person` / `APPROACH_car` | Slowing down near a class-specific stopping distance |
| `STOP_person` / `STOP_car` | Class-specific stop is latched |
| `STOP_OBSTACLE` | Depth-only emergency stop is latched |
| `STOP_MAX_TRAVEL` | Horizontal displacement from the initial position reached the configured limit |

A latched stop prevents forward motion while altitude control remains active with valid odometry. Resetting clears the latch only; it does not reset the takeoff origin or travel limit. An obstacle still in range, or an already exceeded travel limit, can immediately latch the stop again.

## Troubleshooting

| Symptom | Checks and next steps |
| --- | --- |
| Package or launch file not found | Build both packages, then source `/opt/ros/jazzy/setup.bash` and `ros_ws/install/setup.bash` in the current terminal |
| Missing weights or `ultralytics` import error | Run `setup_yolo.sh`, check that `models/yolov8n.pt` exists, and use `run_demo.sh` to expose the Python environment |
| NumPy, OpenCV, or `cv_bridge` import error | Use system Python 3.12 and the setup script's pinned dependencies; build with the virtual environment inactive |
| `WAIT_ODOMETRY` persists | Check `/odom` and `/clock`, confirm Gazebo is running and unpaused, and inspect bridge output |
| `WAIT_PERCEPTION` persists | Check RGB/depth topic rates, perception logs, and local weights; RGB and depth frames must have matching dimensions and close timestamps |
| `WAIT_DEPTH` or `WAIT_OBJECT_DEPTH` persists | Inspect depth images for valid readings; the estimator requires enough finite pixels between 0.15 and 10 m |
| No person/car stop occurs | Inspect `/semantic/annotated` and `/semantic/detections`; recognition depends on camera viewpoint and model confidence |
| Drone remains stopped after reset | Inspect `/semantic/status`; the obstacle may still be present or the travel limit may already be reached |

Useful diagnostic commands, after sourcing ROS and the workspace:

```bash
ros2 topic hz /odom
ros2 topic hz /front_rgbd/image
ros2 topic hz /front_rgbd/depth_image
ros2 topic echo /clock --once
ros2 topic echo /semantic/detections --once
```

## Regenerate scene assets

The procedural generator recreates the tree and outdoor world files. Bundled person/car meshes and textures are preserved:

```bash
python3 ros_ws/src/drone_scene/scripts/generate_outdoor_world.py
```

This overwrites those generated files, including any manual scene edits. Rebuild `drone_scene` afterward to refresh the installed assets.

## Diagnose missing YOLO detections

Keep the demo running and execute this from the repository root in a second terminal:

```bash
source /opt/ros/jazzy/setup.bash
source ros_ws/install/setup.bash
export YOLO_CONFIG_DIR="$PWD/.venv/yolo-config"
.venv/bin/python ros_ws/src/drone_control/scripts/diagnose_yolo.py \
  --weights "$PWD/models/yolov8n.pt"
```

The diagnostic saves `/tmp/drone-yolo-diagnosis.png` and prints all predicted classes at confidence 0.05, including classes filtered out by the flight perception node. It marks predictions that pass the default person/car filter and confidence threshold. This diagnostic does not change controller settings. An empty result means no boxes survived even the diagnostic threshold; lowering confidence alone is not a verified fix. Use the captured image to evaluate better scene assets or train and validate a model on simulation images.

## Limitations

People and cars use bundled textured OSRF meshes. Detection remains dependent on viewpoint, lighting, and the YOLO weights. Validate annotated images and detection/status topics before claiming successful class-based stopping. Asset authors, source identifiers, license notices, and local modifications are recorded in [THIRD_PARTY_ASSETS.md](THIRD_PARTY_ASSETS.md).

The drone uses velocity control with gravity disabled. This is a simulation prototype without an autopilot, obstacle avoidance, or path planning. Missing or stale perception/depth prevents forward motion; missing odometry commands zero velocity. If the controller is forcibly killed, pause or stop Gazebo because the velocity plugin has no independent watchdog.

Recognition can disappear during an approach, particularly when a nearby object is cropped by the camera. The current controller has no target tracking: a fresh frame without an in-path detection can return it to `CRUISE`, until another detection or the depth-only obstacle rule slows or stops it. Earlier successful runs do not guarantee class-based stopping on every run.
